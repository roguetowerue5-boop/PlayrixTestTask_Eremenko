# OfferForge

Локальный инструмент, который собирает офферы целиком: разбирает свободный
заказ продюсера, придумывает несколько вариантов наполнения, генерирует арт
через любой подключённый API, проверяет результат зрением и собирает финальный
композит из отдельных элементов.

Человек вводит тему и пожелания и нажимает одну кнопку. Всё остальное —
включая отбраковку и перегенерацию неудачных картинок — делает пайплайн.

```
run.bat  →  http://127.0.0.1:8848
```

---

## Что происходит за одну кнопку

```
Тема + свободные пожелания
  │
  ├─ brief    разбор заказа в структуру: жанр, настроение, палитра, ограничения
  ├─ concept  fan-out: 3–5 РАЗНЫХ вариантов наполнения + валидация правил
  ├─ render   генерация арта для каждого элемента, со style-референсами и сидом
  ├─ critic   vision-проверка по бинарной рубрике → ретрай неудачных
  └─ compose  сборка композита: фон + арт + рамка + звёзды + текст
```

Каждый этап складывает свои артефакты в `runs/<id>/`: бриф, концепты, промпты,
принятые картинки, **отбракованные картинки с номером попытки**, вердикты QC,
композиты и отчёт. Отбраковка сохраняется намеренно — без неё ход работы
ничем не подтверждается.

---

## Экраны

Слева меню, восемь разделов.

**Генерация** — тема, пожелания, шаблон оффера, пресет моделей. Кнопка и живой лог.

**AI → Провайдеры** — конкретный адрес API и ключ к нему. Одна карточка на провайдера:
поле `API Endpoint`, поле `API Key`, кнопки «Проверить», «Выключить», «Удалить».
«Проверить» ходит настоящим запросом и показывает, сколько моделей доступно и за
сколько миллисекунд ответил сервис. Внизу форма добавления своего API.

Ключи **не** пишутся в `providers.yaml` — он ездит в git. Они лежат в
`config/secrets.json`, который в `.gitignore`. Переменные окружения продолжают
работать как запасной путь: если ключ не введён в интерфейсе, берётся `api_key_env`,
и в карточке появляется метка «из .env».

**Оффер → Разметка UI** — холст со скином, выделение элементов курсором.
Два инструмента: **лассо** (зажал и обвёл по контуру — вырежется ровно
обводка) и прямоугольник для того, что и так прямоугольное. Дальше
выбирается, чем убрать фон вокруг вырезанного — моделью, своим
матированием или ничем. Кнопка «Вырезать элементы» показывает готовый
набор деталей на шахматке.

**Оффер → Сегментация UI** — разбор игрового скина на элементы экрана.
Загружаешь PNG, задаёшь имя версии — получаешь нарезанные панель, ленту,
прогресс-бар, рамку слота, звёзды, бейдж, плашку, крестик и футер плюс набор
референсов стиля.

**Оффер → Сборка оффера** — выбираешь прогон с артом, шаблон и версии
элементов, получаешь готовый экран. Работает на уже сгенерированном арте,
новых запросов к моделям не делает.

**Оффер → Составляющие** — библиотека элементов и разбор эталонной карточки.
Загружаешь карточку, задаёшь имя версии, жмёшь «Разобрать» — vision размечает
элементы, они нарезаются и встают новой версией. Рядом превью всех версий и
кнопка «выбрать» для назначения по умолчанию.

**AI → Модели** — какая модель отвечает за какую задачу. Для каждого варианта:
провайдер, модель, температура (или размер и число референсов у генерации),
кнопка «+ Добавить модель в ротацию» и «Проверить». Проверка гоняет вариант ровно
тем маршрутом, каким пойдёт пайплайн, и показывает результат по каждой модели
ротации отдельно. Сверху — выбор пресета и «Сохранить как…», «Экспорт», «Импорт»,
«Удалить».

**Поведение → Промпты** — список файлов и редактор. Перед сохранением проверяется
синтаксис Jinja2: сломанный шаблон не запишется, а не всплывёт на середине прогона.
Показываются переменные и декораторы, которые шаблон использует, и подсвечиваются
вызовы несуществующих декораторов. Каждое сохранение кладёт предыдущую версию в
`prompts/.backups/` (хранится 20 последних), откат — кнопкой «Бэкапы».

## Идеи, на которых всё держится

### 0. Интерфейс сегментируется, а не генерируется

Генератор сносно рисует предмет и плохо — интерфейс: рамки кривые, надписи
поедут, бейджи не читаются. Поэтому UI не генерируется вообще — он **режется
из готового игрового скина** и дальше собирается композитором.

**Экран «Разметка UI» — основной путь.** Загружаешь скин, выбираешь тип
элемента и обводишь его лассо. Точная разметка бьёт любую автоматику: vision
ставит боксы приблизительно и путает соседние элементы. Если разметка задана,
модель о координатах не спрашивают вовсе.

Почему лассо, а не только прямоугольник: элементы интерфейса редко
прямоугольные. Крестик закрытия круглый, лента с «хвостами», бейдж со
скошенным углом — бокс вокруг любого из них захватывает куски соседей и
подложку панели. Контур повторяет форму, и всё вне него уходит в
прозрачность, так что в библиотеку попадает чистый элемент, а не квадрат с
чужим фоном по краям.

**Вырезанное — это и есть результат, а не полуфабрикат.** Перерисовка
моделью осталась отдельной галочкой: она полезна, когда нужен элемент под
другую палитру или в другом размере, но для сборки оффера из существующего
скина она только вносит расхождения. Оригинальный пиксель точнее любой
перерисовки.

### 0.0. Три бага, из-за которых расходился стиль

Стоит записать, потому что снаружи они выглядели как «модель слабая».

**Референсы не доезжали до модели.** Картинки уходили полем `image`, а
Image API OpenRouter ждёт `input_references` со структурой
`{type, image_url:{url}}`. Незнакомое поле молча выбрасывалось, запрос уходил
с одним текстом, и модель рисовала с нуля. Все рассуждения про «стилевые
референсы с максимальной важностью» всё это время были декларацией — до
модели не доходило ни одного пикселя.

**В английский промпт уходили русские названия.** `TARGET: Название пака` —
и модель добросовестно рисовала эту надпись буквами. У каждого типа
элемента теперь есть поле `en`, оно и идёт в промпт.

**`default_params` применялись только к тексту.** Настройки картинок
(`background: transparent`, `output_format`) никуда не уходили. Теперь
реестр складывает их в запрос, а параметры конкретной модели перекрывают
общие.

Все три закрыты тестами в секции `[3b]` селфтеста: там поднимается
провайдер-шпион и проверяется фактическое тело запроса.

### 0.05. Разметка в два прохода

Одним проходом vision скин не размечает, и это не вопрос выбора модели.
На полном скине 5482×2529 звезда занимает меньше процента кадра. Модель
называет её координаты наугад — отсюда и брались боксы, попадавшие в
пустоту, и вырезанные «куски фона» вместо элементов.

Поэтому проходов два.

**Общий план** ищет только крупное: панель, ленту, прогресс, крестик,
футер и — главное — границы сетки карточек с числом столбцов и строк.
Мелочь внутри карточки в этом промпте не упоминается вовсе, чтобы модель
не пыталась её угадать.

**Крупный план** берёт по найденной сетке ОДНУ карточку, вырезает с
запасом (звёзды сидят над карточкой, плашка свисает ниже) и увеличивает
до 768 пикселей по большей стороне. Там звезда занимает уже десятки
процентов кадра, и модель показывает её уверенно. Координаты ответа
пересчитываются обратно в координаты экрана.

Окно под арт достраивается кодом, а не спрашивается: модель стабильно
путает его с рамкой, а нам оно нужно точно — по нему пробивается
прозрачная дыра.

**Валидация до вырезания.** Vision ошибается предсказуемо: даёт крестику
половину экрана, ставит бокс за границей кадра, забывает сетку. Каждый
бокс проверяется на разумность площади для своего типа, и то, что явно
невозможно, выбрасывается из разметки. Дешевле поймать здесь, чем потом
разбираться по картинкам, почему в библиотеке кусок фона.

### 0.06. Автолассо: точка от модели, контур от кода

Прямоугольный бокс не описывает форму — звезда в нём занимает половину
площади, остальное фон. Обводить контур руками пользователь не должен, а
просить границу у модели бесполезно: она отвечает приблизительно.

Но модель уверенно отвечает на другой вопрос — **где элемент**. Указать
точку на теле звезды ей несложно, это не «проведи границу», а «ткни
пальцем». Дальше границу находит заливка: от точки наружу, пока цвет
похож. Получается то же лассо, только обводит алгоритм.

Поэтому крупный план просит у модели не только бокс, но и `at` — точку на
материале элемента, с прямой оговоркой, что центр бокса не годится: у
звезды он попадает между лучей, у рамки — в пустое окно.

Три вещи, без которых заливка врёт:

- **Дыры заращиваются.** Коричневая цифра на жёлтом бейдже и белая
  надпись на плашке заливку не пропускают и остаются проколами.
  Морфологическое закрытие заодно скругляет внешний контур, поэтому дыры
  ищутся честно: заливаем прозрачное от краёв, что не достигнуто — то
  заперто внутри и закрывается.
- **Заливка фона отбраковывается по углам.** Если точка промахнулась
  мимо элемента, растёт фон вокруг него, а заращивание дыр потом закроет
  им сам элемент. Признак точный: бокс облегает элемент, поэтому в углах
  у любой непрямоугольной формы остаётся фон. Забрала все четыре угла —
  значит это фон.
- **Работа идёт на кропе бокса.** Заливка по полотну 5482×2529 для каждой
  точки — это минуты. На кропе с уменьшением до 640 — доли секунды.

Если точки нет, пробуются несколько кандидатов вокруг центра. Это
костыль на случай молчания модели, и работает он хуже: у крестика все
пробы могут попасть в просветы.

Чего это не заменяет: **разметка курсором всё равно самая точная**.
Автолассо снимает с человека рутину, но там, где элемент сливается с
подложкой по цвету, заливке не за что зацепиться.

### 0.1. Извлечение: три способа снять фон

Вырезать прямоугольник или контур мало. Внутри выделения остаётся то, на
чём элемент лежал: тёмная подложка карточки под звёздами, кант рамки,
угол соседнего бейджа. Нужен не обрезок скрина, а деталь — как в
UI-ките, где каждая кнопка и лента лежат отдельным объектом на
прозрачном фоне. За это отвечает `app/pipeline/extract.py`, и способа
три.

**Моделью** (по умолчанию) — роль `extract` в пресетах. Кроп вместе с
полным экраном уходит в image-edit модель линейки `gemini-*-image`:
единственные в каталоге, кто принимает картинку на вход и возвращает
картинку. Формулировка промпта тут решает всё, поэтому `part_extract.j2`
начинается словами «это задача вырезания, не иллюстрирования» и требует
скопировать пиксели, а не перерисовать. Обычные text-to-image (flux,
qwen) сюда не годятся: у них нет входной картинки, они рисуют заново — и
это ровно то, что давало непохожие элементы раньше.

**Своим матированием** — бесплатно и без сети. Заливка от краёв по
локальной разнице соседей, а не по одному «ключевому» цвету: фон в
игровом UI почти всегда градиентный, и глобальный порог либо не добирает
тёмный край, либо выедает половину элемента. Ограничение честное: если
элемент соприкасается с соседом сплошной границей — звезда лежит на
канте рамки, — они останутся одним куском. Эрозия рвёт тонкие
перемычки, но не сплошной контакт.

**Не убирать** — оставить как вырезано. Нужно, когда фон и есть часть
элемента: панель, футер, лента заголовка.

Отдельная деталь: у групп в библиотеку кладётся **один** экземпляр.
Полоска из пяти звёзд — это пять звёзд, а полоску под нужное число
композитор соберёт сам. Локально это делает разбор на связные
компоненты, у модели — прямое требование в промпте.

Матирование не применяется к тому, что обвели лассо: контур — уже
ручное извлечение, и заливка поверх него пошла бы от края силуэта и
съела сам элемент.

### 0.15. Сверка сборкой

Если детали вырезаны правильно, из них складывается исходный экран. Каждый
элемент возвращается на свои координаты из разметки, результат сравнивается
с оригиналом — что не сошлось, то и вырезано плохо. Это дешевле и честнее,
чем спрашивать модель «хорошо ли получилось»: сборка либо совпадает, либо
нет, и расхождение показывает пальцем на конкретный элемент.

Ловятся два вида брака.

**Дыра** — в оригинале на этом месте что-то есть, в сборке пусто. Элемент
не вырезался или его выело матированием.

**Поглощение** — элемент утащил в себя соседей. Рамка карточки приходит
вместе с плашкой имени, звездой и бейджем: визуально это один объект, и
модель вырезает его целиком. Ловится пересечением: если рамка закрашивает
больше трети площади, отведённой под плашку, значит плашка внутри неё.
Такой элемент на повторной попытке получает прямое требование — только
контур, середина пустая насквозь.

Три детали, без которых проверка врала бы:

- **Карточные элементы размножаются по сетке.** Размечен один слот, а на
  экране их десять. Без размножения сборка отличалась бы девятью пустыми
  слотами, и вина легла бы на панель, которая тут ни при чём.
- **Смещения считаются от своей ячейки, а не от первой.** Разметку делают
  на том слоте, где элемент виднее; бейдж вполне может быть отмечен на
  втором, и отсчёт от первого уводил его за пределы панели.
- **Подложки судят иначе.** Панель и лента по замыслу содержат другие
  элементы, поглощением это считать нельзя. И расхождение внутри панели
  складывается из артов, которых у нас нет и не будет, — оценивается
  только то, что панель вырезалась и заполнена.

**Починка не просит модель — она считает.** Первая версия на найденный
брак отправляла элемент в модель с уточнением «внутри должно быть пусто».
Модель возвращала то же самое: для неё рамка с плашкой — один объект, и
уговоры тут не работают. Но уговаривать и не нужно, всё известно заранее:

- *Поглощение* — вычитаем формы соседей. Координаты заданы разметкой,
  формы уже вырезаны. Вычитается именно форма, а не прямоугольник: плашка
  сидит на нижней перекладине рамки, и убрав прямоугольник, мы срезали бы
  кант вместе с ней. Если собственное извлечение соседа вышло слабым и от
  него осталась одна обводка, берётся область бокса с отступом под кант —
  иначе вычтётся ровно кант, а плашка уцелеет.
- *Пустота* — откатываем к сырому вырезу. Матирование иногда выедает
  элемент почти целиком: ленту заголовка оно оставляет от 91% плотности
  всего 1%. Обрезок скрина с фоном по краям хуже чистого ассета, но
  несравнимо лучше пустоты.

К модели дело доходит только если локальная починка не помогла. Повтор
стартует от исходного обрезка, а не от результата прошлой попытки: иначе
обработка накладывается сама на себя и с каждым разом становится хуже.
Новый вариант принимается, только если брака стало не больше. Локальное
матирование не повторяется вовсе — оно детерминировано.

Отдельно: атомизированные элементы по расхождению не судят. Звёзд в скине
пять подряд, а в библиотеку кладётся одна — она обязана отличаться от
оригинала, и без этого исключения она вечно числилась бы в браке.

В интерфейсе рядом лежат оригинал, сборка и карта расхождений: числа
говорят, что не так, картинки — почему.

### 0.2. Стиль арта: референсы и своя LoRA

Стиль сверяется с `Icons/` — 159 вырезанных карточек из игры. Это лучший
источник правды, какой есть: описание словами всегда приблизительно.

Проверка датасетом уже один раз поправила контекст. По скриншоту казалось,
что арт живописный, и правила были переписаны на painterly — но в
оригинальном разрешении это чистый 3D-рендер с глянцем, и правку пришлось
откатить. Там же выяснилось, что фон карточек первой категории почти всегда
несёт деликатный паттерн — полосы, клетку, волны, — который правила прямо
запрещали.

**Эталонные арты как референсы** — работает без всякого обучения.
`tools/build_lora_dataset.py --art-refs 3` кладёт несколько карточек в
`style/art-refs/`, и они уходят первыми в каждый запрос. Раньше в референсы
шли только куски скина: они задают палитру интерфейса, но молчат о том,
как выглядит сама картинка внутри карточки.

**Своя LoRA** — когда нужно точное попадание. Промптом не передать меру
глянца, характер скруглений и то, как ложится блик. Датасет собирается тем
же скриптом, обучение — на fal.ai или Replicate, подключение — правкой
`providers.yaml` без единой строки кода. Пресет `lora` уже собран: своя
модель первой в ротации, обычные — откатом, чтобы отказ провайдера не
оставлял пустой слот. Подробности и параметры обучения — `lora/README.md`.

Триггер-слово `plrxcard` подставляется первым словом промпта: дообученная
модель узнаёт стиль по нему, а в середине текста токен теряет вес.

**Экран «Сегментация UI» — если размечать лень.** Vision размечает сам,
границы уточняются по альфа-каналу: неточность модели компенсируется
точностью прозрачности. Автосегментация только по альфе не работает —
весь экран там один связный компонент.

Режутся: панель, лента заголовка, прогресс-бар, крестик, футер, рамка слота,
звёзды, бейдж «+N», плашка названия. Плашка и лента приходят с впечатанным
чужим текстом («Star Map», «FARMING») — он затирается растяжкой края, иначе
наша подпись легла бы поверх чужой.

**Вырезанное — это ещё не ассет.** Кусок скриншота приходит с подложкой
панели по краям, без прозрачности, мылом при масштабировании и ровно в том
количестве, в каком элемент встретился на экране. Поэтому есть второй шаг:
**«Перерисовать элементы моделью»**. Каждый кусок уходит в image-модель
референсом с требованием повторить один в один, но изолированно и на чистом
фоне.

**В модель уходит полный экран, а не только обрезок.** Референсов два:
первым — весь скрин как контекст, вторым — вырезанный элемент для деталей,
плюс координаты области в промпте. По одному обрезку модель не понимает ни
назначения элемента, ни его масштаба относительно интерфейса, и рисует
что-то похожее вместо того же самого. Фон срезается заливкой от краёв, у рамки слота дополнительно
выбивается замкнутое окно — иначе она легла бы на арт цветным пятном.

Звёзды генерируются по одной, а полоски на 1–5 собираются кодом: модель,
которую просят нарисовать «пять звёзд в ряд», рисует пять разных с неровным
шагом. Vision сравнивает результат с образцом по силуэту, цвету и чистоте
краёв; не совпало — перерисовка, до трёх попыток.

Вырезанная и перерисованная версии лежат рядом (`orange` и `orange-gen`) и
переключаются одним селектом — видно, что изменилось.

**Вырезанные куски идут в генерацию как референсы.** Это и есть максимальный
приоритет стиля: модель видит не описание словами, а куски того самого
интерфейса, внутри которого будет жить арт. Скин выбирается на экране
генерации; палитра и материалы попадают в цель без уговоров промптом.

**Экран «Сборка оффера».** Готовый арт + элементы скина → финальный экран.
Ни одного запроса к моделям: картинки уже оплачены, пересобирать можно
сколько угодно и бесплатно. Один и тот же прогон собирается всеми четырьмя
скинами за секунды.

### 0.1. Отдельная карточка разбирается так же

Если скина экрана нет, а есть только эталонная карточка — её разбирает экран
«Составляющие» тем же способом, но на карточные элементы.

Типы составляющих: рамка, звёзды, кнопки, цифра с плюсом, название пака, шрифт
и панель набора. Каждый может иметь несколько версий:

```
style/parts/
  index.yaml                    реестр типов, версий и значений по умолчанию
  frame/classic/frame.png       версия «classic»
  frame/из-игры-2026/frame.png  версия, полученная разбором
  stars/classic/1.png … 5.png
  font/classic/part.yaml        шрифт — не картинка, а описание стиля
```

**Экран «Составляющие»** принимает карточку, vision-модель размечает, где
какой элемент, Pillow режет по разметке и складывает новой версией. В рамке
автоматически выбивается прозрачное окно под арт — без этого она легла бы
поверх картинки и закрыла её.

**На экране «Генерация»** для каждого типа выбирается конкретная версия.
Это и есть защита от галлюцинаций: один и тот же набор версий даёт
побайтово одинаковую сборку, а меняется только арт предмета.

```bash
python tools/make_parts.py    # базовая версия classic, чтобы работало из коробки
```

### 0.5. Набор собирается из карточек, а не пересобирает их

`card_set` не раскладывает арт и рамку по отдельности — он вставляет в каждую
ячейку **готовую карточку** по шаблону `card` через слой `kind: template`.

Пока набор дублировал раскладку у себя, рамка растягивалась под размер ячейки,
а звёзд и подписей в наборе не было вовсе. Теперь карточка рисуется в своём
масштабе 512×720 и уменьшается целиком, поэтому оформление в наборе и в
одиночной карточке идентично по построению.

**Режим доводки.** Выбери шаблон «Карточка коллекции» и 1 вариант — получишь
одно изображение за прогон. Правки `style_bible.json` и промптов проверяются
за секунды и центы вместо десяти генераций. Под селектом шаблона показано,
сколько изображений уйдёт на прогон.

### 1. Оффер — это слои, а не картинка

Шаблон оффера описан в YAML как набор слоёв. В нейросеть уходит **только**
слой `kind: image_gen`; рамка, плашка, звёзды и текст собираются локально.

```yaml
layers:
  - { id: matte,  kind: solid,     color: "${palette.0}", box: {...} }
  - { id: art,    kind: image_gen, prompt_slot: art, category: "1", box: {...} }
  - { id: frame,  kind: part,      part: frame,      box: {...} }
  - { id: stars,  kind: part,      part: stars, part_asset: "${rarity}.png", box: {...} }
  - { id: title,  kind: text,      text_slot: title, box: {...} }
```

Шаблон описывает **только раскладку**. Как элементы выглядят — решает
выбранная версия составляющей, поэтому один шаблон собирается разными
наборами элементов без правок.

Что это даёт:

- **Рамки одинаковы по построению.** Их не генерируют — их накладывают.
- **Текст никогда не искажён.** Любая модель испортит `LIFEGUARD TOWER`;
  название рисуется шрифтом с обводкой, модели его не отдают вообще.
- **Правку раскладки видно мгновенно.** Пресет `offline` собирает композит
  на заглушках, без сети и без единого потраченного цента.

`repeat_for` + `grid` размножают слой по сетке — так один слой описывает
десять генераций в наборе.

### 2. Код просит роль, а не модель

Пайплайн никогда не знает, какая модель его исполняет. Он просит **вариант** —
`brief`, `concept`, `copy`, `critic`, `render` — а пресет решает остальное.
Внутри варианта список моделей работает цепочкой фолбэка.

```yaml
variants:
  render:
    model_name: google/gemini-2.5-flash-image
    model_params:
      - { name: google/gemini-2.5-flash-image, provider_id: openrouter_images, n_reference_images: 6 }
      - { name: bytedance/seedream-4.5,        provider_id: openrouter_images, n_reference_images: 4 }
    timeout: 240
```

Готовые пресеты: `budget`, `balanced`, `premium`, `offline`. Свой добавляется
файлом в `model-presets/presets/` плюс строкой в `index.yaml` — код не трогается.
Неизвестный вариант автоматически наследует `default`.

Схема заимствована из `model-presets` SkyrimNet — там ровно та же развязка
роли и модели.

### 3. Кастомный API подключается правкой YAML

Провайдер описывается декларативно: тело запроса и путь к картинкам в ответе
задаются прямо в конфиге. Ни строки кода.

```yaml
internal_art_api:
  kind: custom_rest
  base_url: https://art-api.internal.example
  api_key_env: INTERNAL_ART_API_KEY
  auth_header: X-Api-Key
  auth_scheme: ""
  capabilities: [image]
  image:
    endpoint: /v1/generate
    cost_per_image: 0.02
    body:
      model: "${model}"
      text: "${prompt}"
      resolution: { width: "${width}", height: "${height}" }
      seed: "${seed}"
      style_refs: "${reference_images}"
    response:
      images: "result.artifacts[*].image_b64"
      encoding: base64
```

Доступные `kind`:

| kind | для чего |
|------|----------|
| `openai_compatible` | `/chat/completions` в формате OpenAI — текст и vision |
| `openrouter_images` | унифицированный Image API OpenRouter (`POST /images`) |
| `custom_rest` | произвольный эндпоинт, описанный как выше |

Провайдер без заполненного ключа автоматически пропускается ротацией, а не
роняет прогон. В `providers.yaml` уже лежат выключенные примеры локального
A1111 и внутреннего сервиса.

## Модели по умолчанию

Пресет `budget` включён по умолчанию. Цены сверены с живым каталогом
openrouter.ai на 06.08.2026.

| Пресет | Текст | Арт | Прогон 3×10×4 |
|--------|-------|-----|----------------|
| `budget` | deepseek-v4-flash | flux.2-klein-4b | ~$0.5 |
| `balanced` | minimax на концептах | flux.2-klein-4b | ~$0.6 |
| **`art-premium`** | дешёвый | **gemini-3.1-flash-image** | ~$13 |
| `premium` | claude | gemini-3.1-flash-image | ~$15 |

`art-premium` — то, что стоит брать для доводки визуала: качество упирается
в рендер, а не в токены. Разница между текстовыми пресетами на таком прогоне —
доллар, между рендер-моделями — десятки долларов и весь результат.

DeepSeek не умеет vision — ни в публичном API, ни на OpenRouter, — поэтому
в `critic` его нет и быть не может; там стоит `minimax-m3`.

**Ротация обязана перекрывать разных вендоров.** Это не стилистика, а
следствие граблей: OpenRouter отдаёт `HTTP 403 Access denied by security
policy` для части моделей, и блокировка приходит группой. Цепочка целиком
из моделей одной лаборатории падает вся сразу — фолбэк перестаёт быть
фолбэком. Поэтому вторым-третьим номером всегда идёт другой вендор:
`openai/gpt-5.6-luna`, `google/gemini-3.5-flash-lite`.

`check_models.py` это проверяет и предупреждает, если ротация однородна.

Прогон «3 набора × 10 карточек × 4 варианта» — это ~170 изображений с учётом
отбраковки, то есть около **$0.5** на `budget` и около **$13** на `premium`.
Драйвер счёта — картинки; разница по тексту между пресетами измеряется центами.

В ротацию `render` попадают только модели, принимающие референсные
изображения: без них 30 карточек одного набора расползутся по стилю.

Идентификаторы моделей протухают — провайдер переименовывает, снимает с
публикации, меняет префикс. Проверяется одной командой:

```bash
python tools/check_models.py
```

Скрипт сверяет каждую модель во всех пресетах с публичным каталогом
OpenRouter: существует ли она, умеет ли то, что от неё требует вариант
(vision для `critic`, генерация для `render`), сколько стоит — и отдельно
предупреждает про однородную ротацию, которая ляжет целиком.

### Reasoning ломает JSON-этапы

У текстовых вариантов стоит `reasoning: {effort: none}` в `default_params`.
Это не экономия, а необходимость: DeepSeek V4 Flash и MiniMax рассуждают по
умолчанию, уходят думать на полторы минуты и обрываются на середине ответа,
потому что бюджет токенов кончается до JSON. Снаружи это выглядит как
«модель вернула пустой список», хотя на самом деле пришла одна скобка.

Приложение теперь называет обе ситуации своими именами: `ответ обрезан по
лимиту токенов` и `модель израсходовала бюджет на рассуждения`. Если модель
не понимает параметр `reasoning`, запрос молча повторяется без него.

### Если приходит HTTP 403 «Access denied by security policy»

Ключ принят (иначе был бы 401) и деньги на месте (иначе 402) — запрос
отклонён политикой. Диагностика по одному признаку:

- **403 на моделях одного вендора, на других работает** — ограничение
  конкретного провайдера. Лечится ротацией через другого вендора.
- **403 на моделях разных вендоров подряд** — ограничение уровня аккаунта
  или ключа, модели ни при чём. Смотри на openrouter.ai:
  **Settings → Privacy** (разрешение передавать данные провайдерам),
  IP-allowlist на аккаунте, ограничения самого ключа.

Кнопка «Проверить» у провайдера показывает остаток по ключу и делает
настоящий запрос к модели. Текст ошибки включает `metadata` от OpenRouter —
там видно, какой именно провайдер отказал и по какой причине.

## Правила, которые проверяет код

Требования к набору — не пожелания, а валидаторы. Нарушения чинятся
автоматически, где это возможно детерминированно, и попадают в отчёт:

- ровно N элементов в наборе;
- объекты внутри набора не повторяются;
- присутствуют **все четыре** категории композиции;
- при выключенных золотых карточках категория 5 отклоняется;
- пересечения объектов между вариантами считаются и пишутся в `run_report.md`.

Все эти правила описаны **один раз** — в `style/style_bible.json`, секция
`collection`. Оттуда их читают и промпты (через декораторы `collection_rules()`,
`category_table()`, `rarity_distribution()`, `gold_policy()`), и валидатор
в `app/pipeline/stages.py`. Поправил размер набора или раскладку редкостей в
JSON — изменилось и то, что просят у модели, и то, что проверяется на выходе.

Золотые карточки выключены флагом `collection.gold_cards.enabled: false` —
так требует текущее задание. Поставь `true`, и в набор вернётся категория 5
с персонажами: и промпт, и валидатор подхватят это сами.

## Автономность

QC — это то, что отличает пайплайн от набора промптов. Критик смотрит на
картинку и отвечает бинарной рубрикой: тот ли объект, один ли он и по центру,
соответствует ли композиция категории, нет ли текста внутри арта, нет ли
мелкой детализации, бьётся ли со стилем.

Провал любого пункта → регенерация с уточнением из `fix_hint` и новым сидом,
до трёх попыток. После этого карточка помечается `needs_review` и попадает
в отчёт, а прогон не останавливается.

`run_report.md` считает главную цифру: **сколько прошло с первой попытки** —
до и после включения петли.

> Вариант `critic` требует модель с vision. Публичный API DeepSeek на текущий
> момент text-only, поэтому в `recommended-models.yaml` его в этом варианте
> нет намеренно: без vision этап физически не соберётся, а вместе с ним
> исчезает вся автономность.

## Установка

```bat
run.bat
```

Батник сам создаст venv, поставит зависимости и откроет браузер. Дальше —
**AI → Провайдеры**, вписать ключ в поле `API Key` у `openrouter` и
`openrouter_images`, нажать «Проверить».

Одного ключа хватает на всё: текст, vision и генерация картинок идут через
одного провайдера. Без ключа доступен пресет **Оффлайн (mock)** — пайплайн
проходит целиком на заглушках.

Альтернативно ключ можно положить в `.env` (`OPENROUTER_API_KEY=sk-or-...`) —
интерфейс это увидит и покажет метку «из .env».

Вручную:

```bash
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
python -m uvicorn app.main:app --port 8848
```

## API

| метод | путь | что делает |
|-------|------|-----------|
| `GET` | `/api/config` | пресеты, шаблоны, состояние провайдеров, варианты |
| `POST` | `/api/generate` | прогон, отдаёт прогресс потоком (SSE) |
| `GET` | `/api/runs` · `/api/run/{id}/report` | история и отчёт прогона |
| `GET` | `/api/models?capability=image` | живой список моделей у провайдеров |
| `GET` `PATCH` `POST` `DELETE` | `/api/settings/providers[/{id}]` | провайдеры |
| `POST` | `/api/settings/providers/{id}/test` | живая проверка провайдера |
| `GET` | `/api/settings/variants` | варианты активного пресета |
| `PUT` | `/api/settings/variants/{preset}/{variant}` | ротация моделей варианта |
| `POST` | `/api/settings/variants/{preset}/{variant}/test` | проверка варианта |
| `POST` `DELETE` | `/api/settings/presets[/{id}]` | сохранить как / удалить |
| `GET` `POST` | `/api/settings/presets/{id}/export` · `/import` | экспорт и импорт |
| `GET` `PUT` | `/api/settings/prompts[/{name}]` | список и правка промптов |
| `POST` | `/api/settings/prompts/{name}/validate` · `/restore` | проверка и откат |

## Заметки

- Ключи живут в `.env`, который в `.gitignore`. В репозиторий не попадают.
- `runs/` тоже в `.gitignore` — артефакты прогонов локальные.
- Прогон идёт минутами, поэтому прогресс отдаётся через SSE: молчащий
  спиннер на таком отрезке бесполезен.
- Оптимизировать стоит картинки, а не токены. На прогоне из ~200 изображений
  вся разница между дешёвым и дорогим текстовым пресетом — единицы долларов,
  а цена ошибки в варианте `critic` — потеря автономности целиком.
